## Запись 1 — 2026-08-18: Проектирование Multi-stage Dockerfile
* **Запрос:** «Сгенерируй Multi-stage Dockerfile для NetBox v4.0.8 на базе Python 3.11, чтобы финальный образ не содержал build-essential, запускался от непривилегированного пользователя и был минимального размера».
* **Результат LLM:** Был предложен Dockerfile с 2 стадиями (`python:3.11-alpine`). Однако сборка зависимостей `psycopg2` и `lxml` в alpine потребовала длительной компиляции C-библиотек и вызвала конфликты с musl libc.
* **Действие и адаптация:** Принято решение заменить Alpine на `python:3.11-slim-bookworm`. На первой стадии (`builder`) установлены необходимые заголовочные файлы (`libpq-dev`, `libxml2-dev` и др.) и выполнена сборка wheel-пакетов в `/install`. Во второй стадии (`runtime`) копируются только артефакты и runtime-библиотеки (`libpq5`). Создан non-root пользователь `netbox:netbox` (UID/GID 1000). Размер итогового образа сокращен с 1.4 ГБ до 380 МБ.

## Запись 2 — 2026-08-19: Разработка скрипта setup.sh и строгая совместимость с /bin/sh
* **Запрос:** «Напиши скрипт setup.sh, проверяющий зависимости, генерирующий .env, поднимающий docker compose и ожидающий healthcheck приложения».
* **Результат LLM:** Нейросеть сгенерировала bash-скрипт с конструкциями `function check()`, `[[ -z "$VAR" ]]`, массивами `ARRAY=(...)` и операторами `&> /dev/null`. При запуске через `/bin/sh setup.sh` скрипт завершался с фатальными синтаксическими ошибками (`syntax error: unexpected "function"`).
* **Действие и адаптация:** Полностью переработан синтаксис под стандарт POSIX sh: заменены ключевые слова `function` на стандартные `name()`, условные блоки `[[` заменены на `[`, а перенаправления `&>` заменены на `>/dev/null 2>&1`. Проведена строгая верификация командой `sh -n setup.sh`.

## Запись 3 — 2026-08-19: Обеспечение идемпотентности и сидинга данных
* **Запрос:** «Как сделать так, чтобы при повторном вызове setup.sh не перезаписывались пароли в .env и создавались тестовые записи в NetBox?».
* **Результат LLM:** Предложена перезапись файла с помощью `cat > .env` и запуск отдельного SQL-скрипта через `psql`.
* **Действие и адаптация:** Добавлена проверка `if [ ! -f .env ]; then ... fi`, благодаря чему существующие секреты не стираются при повторных запусках. Вместо сырого SQL использован официальный CLI-интерфейс `manage.py shell` с ORM Django (`Tenant.objects.get_or_create(...)`, `Prefix.objects.get_or_create(...)`), что предотвращает дублирование сущностей и нарушение внешних ключей.

## Запись 4 — 2026-08-20: Настройка GitHub Actions CI Pipeline и симуляция сбоя
* **Запрос:** «Сконфигурируй workflow GitHub Actions для сборки, запуска setup.sh и smoke-тестов. Как продемонстрировать намеренный сбой для отчета?».
* **Результат LLM:** Предложен `.github/workflows/ci.yml` с кэшированием слоев Docker и шагом запуска `smoke_test.sh`.
* **Действие и адаптация:** В пайплайн добавлен предварительный этап синтаксической валидации `sh -n setup.sh && sh -n smoke_test.sh`. Для симуляции сбоя создана тестовая ветка `test-ci-failure`, где в `.env` был передан заведомо неверный пароль PostgreSQL (`DB_PASSWORD=invalid_pass`), в результате чего healthcheck контейнера завершился по таймауту, и GitHub Actions зафиксировал красный статус.

## Запись 5 — 2026-08-20: Стек мониторинга и централизованного сбора логов
* **Запрос:** «Создай конфигурации Prometheus, Grafana, Loki и Promtail для сбора метрик и логов контейнеров NetBox».
* **Результат LLM:** Сгенерированы раздельные docker-compose файлы и конфиг Promtail со static_configs.
* **Действие и адаптация:** Объединен стек мониторинга в единую сеть `monitoring-net` с подключением к сети приложения `netbox-net`. Настроен Promtail с `docker_sd_configs` через сокет `/var/run/docker.sock` для автоматического сбора логов контейнеров с лейблами сервисов. Разработаны 2 JSON-дашборда Grafana (Health и Business metrics) с авто-провижинингом.
